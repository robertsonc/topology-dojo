# Capability Matrix — Topology Dojo

_Compiled 2026-07-19 by a repository-wide code audit (not from prior docs). Every row cites the file:line evidence used to classify it. Classifications:_

- **Shipped-active** — in code, exercised by tests, and live in the current production config (`wrangler.jsonc` top-level).
- **Shipped-behind-flag** — in code and tested, but the flag mechanism is opt-in/opt-out; noted whether the CURRENT production value is on or off.
- **Partial** — real code exists but a documented sub-claim is unmet (e.g., one call site missing a fix applied elsewhere).
- **Documented-not-implemented** — a doc or code comment claims this exists; it does not.
- **Operationally pending** — the code/infrastructure is shipped; a human action outside the repo (a dashboard setting, a drill, a credential) is still required.
- **Deferred / does-not-exist** — no code, intentionally not built yet.

This matrix is the evidentiary basis for `docs/ROADMAP.md`'s "Current Production Baseline" and for `docs/DISCREPANCY_REGISTER.md`. See that register for the specific doc corrections each row implies.

## Cross-cutting notes

- **Every major flag (`WORKSPACE_ENABLED`, `PROFILES_ENABLED`, `ANALYTICS_ENABLED`) is currently `"true"` in the top-level (production) `wrangler.jsonc`.** There is no bootstrapped-but-inert feature left in production as of this audit — all prior "activate later" plans have been executed. Any future roadmap item that says "activate X" about one of these three is stale.
- **The security findings register (`docs/launch-readiness/FINDINGS_REGISTER.md`) understates progress**: the 4 CRITICAL findings (C1–C4) were fixed in commit `a958bce` (2026-07-04) but never annotated as closed in the register — it still reads as if 4 unresolved critical vulnerabilities exist. Two specific HIGH/MEDIUM findings (H1, M20) were independently re-verified this audit and **are** still genuinely open in code.
- **Zero open GitHub Issues, zero open PRs, 174 merged PRs (#1–#195), 7 stale-but-fully-merged branches.** This repository does not use GitHub Issues as a planning tool; all planning lives in `docs/`. This shaped the decision to deliver `docs/PACKET_ISSUES.md` as issue-ready Markdown rather than opening ~20 live issues unilaterally into a tracker this project has never used.
